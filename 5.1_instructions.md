## Estructura de Salida Requerida

### 5.1.1 Backend Application Core Testing Suite
Analiza la carpeta o proyectos de pruebas (usualmente terminan en `.Tests` o `.UnitTests`) y genera:
- **Estrategia de Pruebas:** Describe el enfoque utilizado. Busca evidencias de Pruebas Unitarias (AAA: Arrange-Act-Assert), Pruebas de Integración (ej. usando `WebApplicationFactory`) y Pruebas de Sistema/E2E si aplican.
- **Pruebas BDD (Gherkin/SpecFlow):** Busca archivos `.feature`. Si no existen, **propón escenarios Gherkin** críticos basados en las funcionalidades principales (ej. US44 Login, US33 Listar Dispositivos IoT) que el sistema debería cumplir.
- **Herramientas:** Identifica y menciona los frameworks utilizados analizando los archivos `.csproj` (ej. xUnit, NUnit, Moq, FluentAssertions, SpecFlow). Menciona la estrategia de cobertura de código.

### 5.1.2 Pattern Based Backend Application(s)
Analiza el código fuente (Controladores, Servicios, Repositorios) y busca evidencias de patrones de diseño clásicos (GoF) y arquitectónicos implementados en .NET. Muestra **fragmentos de código** (snippets cortos) como evidencia. Busca específicamente:
- **Singleton / Dependency Injection:** Identifica cómo se registran los servicios en `Program.cs` o `Startup.cs` (ej. `builder.Services.AddSingleton()`, `AddScoped()`). Explica qué rol cumplen.
- **Facade / Service Layer:** Busca clases de servicio (ej. `IAuthService`, `DeviceService`) que coordinan la lógica de negocio para que los Controladores (`ControllerBase`) permanezcan "limpios".
- **Adapter / Mapper:** Identifica el uso de clases que transforman entidades de base de datos a DTOs (Data Transfer Objects). Revisa si se usa librerías como AutoMapper o métodos de extensión manuales.
- **Chain of Responsibility / Middleware:** Analiza la configuración del pipeline en `Program.cs` (ej. `app.UseAuthentication()`, middlewares personalizados) para el manejo transversal de peticiones (JWT, CORS, etc.).
- **Proxy / Repository:** Identifica si se usa el patrón Repositorio para abstraer Entity Framework Core (`DbContext`), actuando como un proxy hacia la base de datos.

Si luego encuentras otros patrones, tambien puedes documentarlos.

### 5.1.3 Pattern Based Custom Software Library
Identifica si existe un proyecto de biblioteca de clases (`Class Library`) compartido (ej. `IoBuild.Common`, `IoBuild.Shared`, `IoBuild.Core`).
- **Contenido:** Describe qué componentes transversales y reutilizables existen (ej. Middleware de manejo global de excepciones, utilitarios de JWT, modelos de respuesta estándar, enums compartidos).
- **Justificación:** Explica desde el punto de vista arquitectónico cómo esta librería reduce la duplicación de código entre los diferentes microservicios (IAM, Device Management, Projects) y promueve la mantenibilidad.

### 5.1.4 Framework Pattern Driven Refactoring Report
Basándote en el concepto de "evolución arquitectónica" hacia microservicios descrita en `ADD_iteration_n_IoBuild.md`, redacta el informe de refactorización:
- **Estado Inicial (El Problema):** Describe hipotéticamente (o basado en código legado si existe) un código monolítico inicial, con lógica de acceso a datos mezclada directamente en los endpoints o controladores, alto acoplamiento y sin separación de responsabilidades.
- **Estado Refactorizado (La Solución):** Describe la arquitectura actual. Destaca la separación en capas lógicas (API -> Business Logic -> Data Access), el uso estricto de Inyección de Dependencias promovido por .NET, y la segregación de responsabilidades.
- **Impacto:** Concluye mencionando la mejora en testeabilidad, mantenibilidad y la gestión centralizada de errores (ej. mediante un `GlobalExceptionHandlerMiddleware` o filtros de excepciones).

1. **Veracidad y Proactividad:** Debes leer el código real. Si un patrón no se llama exactamente como en el GoF, pero cumple la función (ej. un Middleware actuando como Chain of Responsibility), documéntalo y explícalo. 2. **Formato:** Usa una estructura jerárquica clara (Markdown), tablas para resumir y bloques de código (`csharp`) cortos para las evidencias.
3. **Mapeo de Código:** Siempre que menciones un patrón o estrategia, indica el **nombre exacto del archivo, clase o método** de la solución IoBuild que sirve como prueba.
4. **Trazabilidad:** Referencia las decisiones de diseño documentadas en `ADD_iteration_n_IoBuild.md` (ej. "Se implementó el patrón *X* en el microservicio *Y* para satisfacer el driver QA-1 de Seguridad").
